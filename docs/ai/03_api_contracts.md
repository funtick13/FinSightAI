# 03. Контракты API между backend и AI‑сервисом

## Обзор

AI‑сервис предоставляет HTTP REST API для взаимодействия с backend‑ом. Контракт определяет, какие данные должен отправлять backend, и какой формат ответа возвращает AI‑сервис. Соблюдение контракта гарантирует, что оба сервиса работают согласованно и что аналитическая логика может эволюционировать без изменения интерфейса.

## Эндпойнты

### `GET /health`

Проверка доступности сервиса. Возвращает JSON `{ "status": "OK" }` или HTTP‑статус 200 без тела. Используется для мониторинга и балансировщиков.

### `POST /analysis`

Основной эндпойнт для анализа финансовых операций. Принимает `AnalysisRequest` и возвращает `AnalysisResponse`.

* **Request body (JSON)** — объект `AnalysisRequest`:
  - `userId` (`string`) — идентификатор пользователя, для которого выполняется анализ.
  - `period` (`string`) — период в формате `YYYY-MM` или другой формат, определённый в ТЗ.
  - `bank` (`string`) — название банка или источник выписки.
  - `statementIds` (`array<string>`) — список идентификаторов выписок, которые были распарсены и переданы на анализ.
  - `transactions` (`array<TransactionDto>`) — список транзакций с полями:
    - `id` (`string`) — идентификатор операции;
    - `date` (`string`) — дата операции;
    - `amount` (`number`) — сумма (доход > 0, расход < 0);
    - `category` (`string`) — категория;
    - `description` (`string`, optional) — описание;
    - `currency` (`string`, optional) — валюта.

* **Response body (JSON)** — объект `AnalysisResponse`:
  - `status` (`string`) — код статуса обработки (`SUCCESS`, `NO_DATA`, `INVALID_INPUT`, `ANALYSIS_ERROR`, `INTERNAL_ERROR`).
  - `summary` (`SummaryDto`) — суммарные показатели:
    - `totalIncome` — общая сумма доходов;
    - `totalExpense` — общая сумма расходов (положительное число);
    - `balance` — разница `totalIncome – totalExpense`;
    - `period` — анализируемый период;
    - `currency` — валюта (если операции различной валюты суммируются, указывается базовая).
  - `categoryAnalytics` (`array<CategoryAnalyticsDto>`) — список категорий расходов с полями:
    - `category` — название категории;
    - `amount` — сумма расходов по категории;
    - `percent` — процент от общего расхода;
    - `operationsCount` — количество операций в категории.
  - `topCategories` (`array<CategoryAnalyticsDto>`) — первые три элемента из `categoryAnalytics`.
  - `financialState` (`string`) — финансовое состояние, определённое модулем `StatePredictor`.
  - `insights` (`array<InsightDto>`) — текстовые инсайты; каждый объект включает `text` и, при необходимости, дополнительные поля (например, `category` или ключевые показатели).
  - `recommendations` (`array<RecommendationDto>`) — список рекомендаций (от 2 до 5). Каждый объект содержит `text`, `type` (например, `EXPENSE_OPTIMIZATION`, `SAVING`, `WARNING`) и, при необходимости, связанные категории или показатели.

### Ошибки

Сервис может возвращать следующие коды статуса:

- **`SUCCESS`** — анализ выполнен успешно, заполнены все поля ответа.
- **`NO_DATA`** — список транзакций пуст; сервис не может выполнить анализ и возвращает пустые поля.
- **`INVALID_INPUT`** — входные данные некорректны (например, отсутствуют обязательные поля или суммы не являются числами).
- **`ANALYSIS_ERROR`** — ошибка в процессе анализа (например, ошибка логики).
- **`INTERNAL_ERROR`** — внутренняя ошибка сервиса (например, ошибка базы данных).

В случае ошибки статус заполняется соответствующим значением, а поля результата могут быть пустыми. Backend использует `status` для отображения сообщений пользователю и решения, нужно ли повторно вызывать сервис.

## OpenAPI‑описание

Для документирования API рекомендуется предоставить спецификацию в формате OpenAPI 3.0 (`openapi/ai-service.yaml`). Она должна описывать все эндпойнты, схемы запросов и ответов, статусы и примеры. Наличие спецификации позволяет генерировать клиентские SDK и автоматически проверять контракт при интеграционных тестах.
