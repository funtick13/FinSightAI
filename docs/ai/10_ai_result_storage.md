# 10. Хранение результатов анализа

## Назначение

После выполнения анализа AI‑сервис возвращает в backend результат `AnalysisResponse`. Backend должен сохранить этот результат, чтобы пользователи могли просматривать аналитику за прошлые периоды, а также для обучения будущих моделей. Этот документ описывает предлагаемую схему хранения результатов в базе данных PostgreSQL.

## Сущности и связи

### `FinancialAnalysis`

Основная сущность, представляющая один акт анализа. Поля:

- `id` — первичный ключ.
- `user_id` — идентификатор пользователя (foreign key на таблицу пользователей).
- `period` — анализируемый период (например, `2026‑03`).
- `bank` — название банка или источник выписки.
- `total_income` — суммарная сумма доходов.
- `total_expense` — суммарная сумма расходов.
- `balance` — разница `total_income – total_expense`.
- `financial_state` — состояние, определённое `StatePredictor`.
- `status` — код статуса (`SUCCESS`, `NO_DATA`, `INVALID_INPUT`, `ANALYSIS_ERROR`, `INTERNAL_ERROR`).
- `created_at` — дата и время выполнения анализа.

### `CategoryAnalytics`

Представляет агрегированную информацию по каждой категории расходов в рамках одного анализа. Поля:

- `id` — первичный ключ.
- `analysis_id` — внешний ключ на `FinancialAnalysis`.
- `category` — название категории.
- `amount` — сумма расходов по категории.
- `percent` — процент от общего расхода.
- `operations_count` — количество операций.
- `is_top` — булево значение, отмечающее, входит ли категория в топ‑3.

### `Insight`

Описание одного инсайта. Поля:

- `id` — первичный ключ.
- `analysis_id` — внешний ключ на `FinancialAnalysis`.
- `type` — тип инсайта (`CATEGORY_STRUCTURE`, `INCOME_EXPENSE_RATIO`, и др.).
- `text` — текст инсайта.
- `data` — опциональное поле JSON с дополнительной информацией (например, {"category": "Еда", "percent": 0.4}).

### `Recommendation`

Хранит одну рекомендацию. Поля:

- `id` — первичный ключ.
- `analysis_id` — внешний ключ на `FinancialAnalysis`.
- `type` — тип рекомендации (`EXPENSE_OPTIMIZATION`, `BUDGET_CONTROL`, `SAVING`, `WARNING`, `GENERAL_ADVICE`).
- `text` — текст рекомендации.
- `data` — опциональное поле JSON с параметрами (например, {"targetPercent": 10}).

## Диаграмма ERD

Рекомендуется составить ER‑диаграмму, демонстрирующую связи между таблицами. В упрощённом виде:

```
FinancialAnalysis 1---n CategoryAnalytics
FinancialAnalysis 1---n Insight
FinancialAnalysis 1---n Recommendation
```

Каждый анализ может иметь много категорий, инсайтов и рекомендаций. Категории, инсайты и рекомендации связаны только с конкретным анализом и не используются повторно между пользователями или периодами.

## Особенности реализации

1. **Нормализация.** Категории и рекомендации хранятся отдельно от основной таблицы, что упрощает добавление и изменение записей.
2. **Масштабируемость.** При большом количестве анализов рекомендуется добавить индексы по полям `user_id` и `period` для ускорения выборок.
3. **Хранение JSON.** Поля `data` можно хранить в типе `JSONB` PostgreSQL для гибкости и быстрого поиска по ключам.
4. **Историчность.** Записи не изменяются после создания (анализ за период не перезаписывается), что позволяет отслеживать изменения финансового поведения во времени.

Такое хранилище позволяет backend‑у быстро выбирать аналитику по пользователю и периоду, отображать историю изменений и использовать данные для обучения ML‑моделей в будущем【turn2file0†L31-L41】.
