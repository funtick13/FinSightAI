# 11. Обработка ошибок и статусов

## Введение

AI‑модуль должен корректно реагировать на некорректные входные данные, отсутствие данных и внутренние ошибки. Вместо того чтобы возвращать исключения или обрыв соединения, сервис отвечает структурированным JSON с кодом статуса. Backend использует этот статус для отображения сообщения пользователю и решения, нужно ли повторять анализ. Этот документ описывает возможные статусы и рекомендации по обработке ошибок【turn2file0†L31-L41】.

## Коды статусов

| Код | Описание | Ситуации использования |
|-----|----------|-----------------------|
| **`SUCCESS`** | Анализ выполнен успешно. Все поля в `AnalysisResponse` заполнены. | Список транзакций непустой и валиден; расчёты выполнены без ошибок. |
| **`NO_DATA`** | Нет данных для анализа. | Список транзакций пуст или все суммы равны нулю. В `AnalysisResponse` поля могут быть пустыми, а `financialState` = `NO_DATA`. |
| **`INVALID_INPUT`** | Некорректные входные данные. | Отсутствуют обязательные поля (`userId`, `transactions`), неверный формат даты, `amount` не является числом, отсутствует `category`. |
| **`ANALYSIS_ERROR`** | Ошибка в процессе анализа. | Например, возникла ошибка при группировке категорий, деление на ноль при вычислении процентов, некорректная конвертация валюты. |
| **`INTERNAL_ERROR`** | Внутренняя ошибка сервиса. | Неожиданное исключение, связанное с инфраструктурой (например, недоступность БД или зависимого сервиса). |

## Обработка на стороне AI‑сервиса

1. **Валидация запроса.** Перед началом анализа сервис проверяет наличие обязательных полей. При отсутствии — возвращает `INVALID_INPUT` с описанием, какие поля отсутствуют.
2. **Обработка пустых данных.** Если список транзакций пуст, сервис возвращает `NO_DATA` и не вызывает анализ. `Summary`, `categoryAnalytics`, `topCategories`, `insights` и `recommendations` могут быть пустыми, а `financialState` = `NO_DATA`【turn2file0†L31-L41】.
3. **Логирование ошибок.** Все ошибки логируются (уровни WARNING/ERROR), чтобы разработчики могли их исследовать. В ответе клиенту передаётся только код статуса и краткое сообщение без деталей реализации, чтобы не раскрывать внутреннюю структуру.
4. **Защита от падения.** Даже при исключениях сервис должен возвращать JSON с `status = INTERNAL_ERROR`, чтобы backend мог корректно обработать ошибку и сообщить пользователю.

## Обработка на стороне backend‑а

1. **Перенаправление ошибок.** Backend не должен пытаться интерпретировать ошибки AI‑сервиса. Получив статус `INVALID_INPUT`, backend может проверить входные данные и скорректировать запрос. При `NO_DATA` backend может сообщить пользователю, что для данного периода нет транзакций.
2. **Повторные попытки.** Для статусов `ANALYSIS_ERROR` и `INTERNAL_ERROR` backend может попробовать повторить запрос спустя некоторое время или показать пользователю сообщение о временной недоступности аналитики.
3. **Сохранение ошибок.** Backend может сохранять ошибки анализа в отдельной таблице для дальнейшего анализа и улучшения сервиса.

## Пример ответа об ошибке

```json
{
  "status": "INVALID_INPUT",
  "summary": null,
  "categoryAnalytics": [],
  "topCategories": [],
  "financialState": null,
  "insights": [],
  "recommendations": [],
  "message": "Поле transactions обязательно"
}
```

Поле `message` в ответе не стандартизировано в ТЗ, но может быть добавлено для упрощения отладки. В production‑режиме рекомендуется избегать подробных сообщений об ошибке, чтобы не раскрывать внутренние детали.
