## 12. Требования к интеграции подсистемы управления банковскими выписками

### Назначение

Подсистема управления банковскими выписками предназначена для загрузки, хранения, просмотра и удаления банковских выписок пользователей в рамках приложения FinSight AI. Она реализуется на стороне backend‑сервера (Spring Boot) и взаимодействует с мобильным приложением через REST API. На текущем этапе система работает только с файлами выписок и их метаданными; парсинг PDF, извлечение транзакций и аналитика выполняются на следующих этапах.

После интеграции пользователи должны иметь возможность:

- загружать выписки в формате PDF;
- видеть список загруженных выписок и их статусы;
- получать метаданные конкретной выписки;
- удалять выписки;
- работать только со своими данными.

### Общее описание

1. **Принцип единого владельца.** Каждый файл выписки принадлежит конкретному пользователю. Пользователь может просматривать, скачивать и удалять только свои выписки. Запросы других пользователей к этой выписке должны возвращать ошибку доступа.

2. **Поддерживаемый банк.** В рамках MVP поддерживается только банк `SBERBANK`. Дополнение банков возможно в будущем, но должно сопровождаться расширением перечисления `BankType`.

3. **Поддерживаемый формат.** Принимаются только файлы в формате PDF. Попытка загрузить файл другого типа (JPEG, PNG, ZIP и т. п.) должна приводить к ошибке `INVALID_FILE_TYPE`.

4. **Ограничение размера.** Максимальный размер файла выписки устанавливается на стороне backend. При превышении лимита API возвращает ошибку `FILE_TOO_LARGE`.

5. **Хранение файлов.** Физические файлы выписок сохраняются в файловой системе backend‑сервера или в отдельном хранилище. В базе данных хранится только путь к файлу и сопутствующие метаданные; файл не должен сохраняться в базе как BLOB.

6. **Статусы выписок.** Каждая выписка находится в одном из четырёх состояний:

   * `UPLOADED` — файл успешно загружен;
   * `PROCESSING` — файл находится в обработке (статус зарезервирован для будущего этапа парсинга);
   * `PROCESSED` — обработка успешно завершена (в дальнейшем при наличии парсинга);
   * `FAILED` — произошла ошибка при обработке.

   Текущий этап использует только `UPLOADED`, но модель должна предусматривать остальные состояния для поддержки будущего расширения.

7. **Безопасность.** Все запросы к API выписок должны требовать аутентификацию. Backend должен удостовериться, что пользователь обладает правами на запрашиваемый ресурс. Доступ неавторизованного пользователя должен быть заблокирован.

8. **Валидация данных.** Backend выполняет проверку параметров запроса (валидность периода, поддержка банка, наличие файла) и возвращает информативные сообщения об ошибках. Ошибки должны иметь код и текстовое описание.

### Модель данных `Statement`

Сущность `Statement` представляет собой банковскую выписку и имеет следующие поля:

| Поле               | Тип данных          | Обязательное | Описание                                                     |
|--------------------|---------------------|--------------|--------------------------------------------------------------|
| `id`               | UUID                | Да           | Уникальный идентификатор выписки                             |
| `userId`           | UUID                | Да           | Идентификатор владельца выписки                              |
| `bank`             | `BankType`          | Да           | Банк, которому принадлежит выписка                           |
| `period`           | строка              | Да           | Расчётный месяц в формате `YYYY-MM`                          |
| `originalFileName` | строка              | Да           | Имя загруженного файла                                       |
| `storedFileName`   | строка              | Да           | Внутреннее имя файла в хранилище                             |
| `filePath`         | строка              | Да           | Путь к файлу в файловой системе                              |
| `fileSize`         | число               | Да           | Размер файла в байтах                                        |
| `contentType`      | строка              | Да           | MIME‑тип файла (например, `application/pdf`)                 |
| `status`           | `StatementStatus`   | Да           | Текущий статус обработки выписки                             |
| `uploadedAt`       | datetime            | Да           | Дата и время загрузки                                        |
| `processedAt`      | datetime \| null    | Нет          | Дата завершения обработки (на данном этапе остаётся `null`)  |
| `errorMessage`     | строка  \| null     | Нет          | Сообщение об ошибке (если статус `FAILED`)                   |

### Перечисления

#### `BankType`

Перечисление банков. На этапе MVP содержит одно значение:

    SBERBANK

#### `StatementStatus`

Перечисление статусов обработки выписки:

    UPLOADED    — выписка загружена и ожидает обработки
    PROCESSING  — выписка находится в обработке (зарезервировано)
    PROCESSED   — выписка обработана успешно (зарезервировано)
    FAILED      — обработка завершилась ошибкой (зарезервировано)

### API интеграции

#### Загрузка выписки

**POST `/api/statements`** — загружает PDF‑выписку. Запрос отправляется от имени авторизованного пользователя.

Параметры запроса (`multipart/form-data`):

- `file` — файл выписки (обязателен); должен быть PDF;
- `bank` — код банка (`SBERBANK`);
- `period` — строка в формате `YYYY-MM` (период выписки).

Ответ (`201 Created`):

    {
      "id": "uuid",
      "status": "UPLOADED"
    }

#### Получение списка выписок

**GET `/api/statements`** — возвращает список выписок текущего пользователя.

Query‑параметры (необязательные):

- `period` — фильтр по периоду (`YYYY-MM`);
- `bank`  — фильтр по банку (`SBERBANK`).

Ответ (`200 OK`): массив объектов `Statement` (без полей `storedFileName` и `filePath`).

#### Получение одной выписки

**GET `/api/statements/{id}`** — возвращает метаданные конкретной выписки. Backend должен проверить, что выписка принадлежит текущему пользователю.

Ответ (`200 OK`): объект `Statement`.

Если выписка не найдена или принадлежит другому пользователю, возвращается ошибка `STATEMENT_NOT_FOUND`.

#### Удаление выписки

**DELETE `/api/statements/{id}`** — удаляет выписку и физический файл. Метод доступен только владельцу выписки.

Ответ (`204 No Content`).

При удалении должны быть удалены запись в базе данных и файл из хранилища. При невозможности удалить файл статус должен стать `FAILED`, а поле `errorMessage` должно содержать причину.

### Требования к обработке ошибок

Подсистема должна возвращать структурированные ошибки. Ошибка содержит код (`code`) и сообщение (`message`). Допустимые коды ошибок:

- `INVALID_FILE_TYPE` — загруженный файл имеет неподдерживаемый формат;
- `FILE_TOO_LARGE` — файл превышает максимальный размер;
- `UNSUPPORTED_BANK` — банк не поддерживается системой;
- `INVALID_PERIOD` — некорректный формат периода;
- `STATEMENT_NOT_FOUND` — выписка не найдена или не принадлежит пользователю;
- `ACCESS_DENIED` — попытка доступа без авторизации или к чужой выписке;
- `FILE_STORAGE_ERROR` — ошибка при сохранении/удалении файла;
- `UNAUTHORIZED` — пользователь не авторизован.

Пример структуры ошибки:

    {
      "code": "INVALID_FILE_TYPE",
      "message": "Файл должен быть в формате PDF"
    }

### Ограничения MVP

На этапе интеграции подсистема выписок должна соответствовать следующим ограничениям:

- поддерживается только банк `SBERBANK`;
- принимаются только PDF‑файлы;
- пользователь может взаимодействовать только со своими выписками;
- парсинг PDF и извлечение транзакций отсутствуют;
- аналитика и вызов AI‑сервиса отсутствуют;
- очереди, вебхуки и асинхронные события не используются;
- размер файла ограничен (значение задаётся конфигурацией backend).

### Ожидаемый результат интеграции

После внедрения подсистемы управления выписками backend FinSight AI должен:

1. Предоставлять API для загрузки, просмотра и удаления PDF‑выписок.
2. Сохранять файлы выписок в хранилище и метаданные в базе данных.
3. Гарантировать, что каждый пользователь видит только свои выписки.
4. Поддерживать базовую систему статусов для дальнейшего расширения (включая обработку и ошибки).
5. Возвращать информативные и структурированные сообщения об ошибках.

Такая интеграция подготовит инфраструктуру для последующих этапов, когда будут реализованы парсинг PDF, извлечение транзакций, их хранение и вызов AI‑сервиса для анализа финансовых данных.
