# 13. План тестирования AI‑модуля

## Цели тестирования

Тестирование AI‑модуля FinSight AI направлено на проверку корректности расчётов, устойчивости к ошибкам и соответствия API‑контракту. План охватывает уровень модулей (unit‑тесты), интеграционный уровень (тесты API) и контрактный уровень (совместимость backend ↔ AI‑сервис). Кроме того, следует проверить сценарии с пустыми и некорректными данными.

## Виды тестов

### 1. Unit‑тесты для каждого модуля

**`AnalyticsProvider`**

- Корректность расчёта `totalIncome`, `totalExpense` и `balance` для различных сочетаний доходов и расходов.
- Группировка по категориям: проверка сумм, процентов, сортировки и выбора топ‑3.
- Обработка пустого списка операций (возврат `NO_DATA`).
- Обработка операций с разными валютами (если реализована конвертация).

**`StatePredictor`**

- Проверка всех rule‑based сценариев: возвращается ли правильное состояние при различных отношениях доходов/расходов и долях категорий.
- Граничные значения для порогов (например, ровно 35 %, ровно 0.8).
- Поведение при `totalExpense = 0` и `totalIncome = 0`.

**`PatternDetector`**

- Обнаружение паттернов: превышение расходов над доходами, концентрация в одной категории, суммарное преобладание топ‑3 категорий, крупные платежи, частые мелкие траты, отсутствие доходов.
- Проверка, что паттерны возвращаются с корректными данными (`percent`, `amount`, количество операций).

**`InsightGenerator`**

- Корректность генерации текстов для каждого типа инсайта (структура расходов, соотношение доходов и расходов, крупные покупки, мелкие траты, отсутствие доходов, высокая концентрация).
- Проверка локализации (если поддерживается) и форматирования чисел.
- Проверка ограничения количества инсайтов (3–5) и приоритетности.

**`RecommendationGenerator`**

- Правильный выбор типа рекомендации в зависимости от паттернов и финансового состояния.
- Корректность подстановки числовых значений в шаблоны.
- Проверка ограничения количества рекомендаций (2–5) и сортировки по приоритету.

### 2. Интеграционные тесты API

Тесты, проверяющие корректность взаимодействия через HTTP:

- Запрос `POST /analysis` с валидными данными должен возвращать статус 200 и `AnalysisResponse` с правильными значениями.
- Запрос `POST /analysis` с пустым списком операций → `status = NO_DATA`.
- Запрос `POST /analysis` с некорректным JSON → `status = INVALID_INPUT`.
- Поведение сервиса при внутренних исключениях: должен возвращать `INTERNAL_ERROR`, а не HTTP 500.

### 3. Контрактные тесты backend ↔ AI‑service

Проверяют соответствие API‑контракта (`openapi/ai-service.yaml`):

- backend использует корректные поля при формировании `AnalysisRequest`;
- AI‑сервис возвращает ожидаемые поля и типы данных в `AnalysisResponse`;
- изменения в API должны сопровождаться обновлением спецификации OpenAPI и тестов.

### 4. Тестирование граничных и негативных сценариев

- Транзакции с экстремально большими суммами (границы типов данных).
- Операции только доходы или только расходы.
- Категории с одинаковой суммой (проверка сортировки и выбора топ‑3).
- Наличие некорректных категорий или пустых строк.

## Логирование и мониторинг

Тесты также должны проверять, что сервис корректно логирует ошибки. При выполнении интеграционных тестов можно эмулировать отказ зависимостей (например, базы данных) и убедиться, что сервис возвращает `INTERNAL_ERROR` и пишет запись в лог.

## Инструменты тестирования

- **PyTest** или аналог — для unit‑ и интеграционных тестов.
- **HTTPX** или **requests** — для тестирования API.
- **Schemathesis** — для контрактного тестирования API на основе OpenAPI‑спецификации.

## Непрерывная интеграция

Рекомендуется настроить автоматический запуск тестов при каждом коммите или Pull Request. Провалившиеся тесты должны блокировать слияние кода. Такой подход обеспечивает стабильность сервиса и позволяет быстро обнаруживать регрессии.
