# Обзор архитектуры

Данный документ описывает архитектуру системы **FinSight AI** на высоком
уровне.  Его цель — показать, как взаимодействуют различные компоненты,
и создать общее понимание для всех участников разработки.  Система
следует принципам микросервисной архитектуры: мобильное приложение,
серверная часть и AI‑сервис разрабатываются и разворачиваются отдельно.
Общение между ними происходит через чётко определённые API.

## Компоненты

### Мобильное приложение (Flutter)

Мобильное приложение является основной точкой входа для пользователя.
Оно отвечает за регистрацию, вход, загрузку PDF‑выписок, отображение
аналитики и рекомендаций и за общий пользовательский опыт.  Приложение
не содержит бизнес‑логики и не хранит данные; вместо этого оно
взаимодействует с сервером через HTTP‑запросы.

### Серверная часть (Spring Boot)

Сервер играет роль координатора и основного хранилища данных.
Он предоставляет REST‑эндпоинты для аутентификации, загрузки и
управления выписками, хранения операций, вычисления аналитики и
работы с профилем пользователя.  Когда пользователь загружает
выписку, сервер сохраняет файл на диск, записывает метаданные в
базу данных и инициирует асинхронный парсинг (на поздних этапах
через очередь сообщений).  Сервер также взаимодействует с AI‑сервисом
для преобразования сырых операций в агрегированную аналитику и
рекомендации.

### AI‑сервис (Python)

Этот сервис инкапсулирует «интеллектуальную» часть системы.
Изначально он реализует правило‑ориентированный движок, который
принимает список операций и возвращает агрегированные итоги,
инсайты и персональные рекомендации.  AI‑сервис реализован на
FastAPI и предоставляет эндпоинты, используемые серверной частью.
В будущих версиях он может быть заменён или дополнен моделями
машинного обучения.

### База данных

Реляционная база данных (PostgreSQL) хранит пользователей, выписки,
операции и данные аналитики.  Такие сущности, как `User`,
`Statement`, `Operation` и `MonthlyAnalytics`, сохраняются здесь.
Схема базы данных развивается параллельно с кодовой базой.
Прямой доступ к базе имеет только сервер.

### Файловое хранилище

Загруженные PDF‑выписки сохраняются на файловой системе сервера в
каталоге `storage/`.  Каждый файл называется уникальным
идентификатором.  В базе данных хранится ссылка на путь к файлу и
метаданные о банке, месяце и пользователе.  При необходимости
такой способ можно заменить объектным хранилищем (например, S3).

## Поток данных

1. **Регистрация и вход** — пользователь создаёт учётную запись и
   проходит аутентификацию через сервер.  Выпускаются JWT или
   сессионные куки, которые используются для последующих запросов.
2. **Загрузка выписки** — мобильное приложение отправляет на сервер
   PDF‑выписку.  Сервер проверяет файл, сохраняет его на диск и
   записывает метаданные в базу данных.
3. **Парсинг** — сервер инициирует асинхронный разбор загруженного
   файла.  Парсер извлекает операции (дата, сумма, описание,
   категория).  Дубликаты отфильтровываются.
4. **Анализ** — сервер отправляет список операций в AI‑сервис.  AI‑сервис
   возвращает агрегированные итоги, разбивку по категориям и
   рекомендации.
5. **Сохранение** — сервер сохраняет разобранные операции и результаты
   анализа в базе данных.
6. **Представление** — мобильное приложение запрашивает у сервера
   данные аналитики и рекомендации и показывает их пользователю.

## Асинхронная обработка

Хотя MVP может обрабатывать выписки синхронно, архитектура системы
предусматривает асинхронное выполнение.  После загрузки выписки
сервер помещает задачу парсинга в очередь сообщений.  Рабочий процесс
(либо часть сервера, либо отдельный сервис) забирает задачу,
извлекает операции и вызывает AI‑сервис.  Интерфейс пользователя
может опрашивать сервер для получения статуса и отображать
индикаторы прогресса.

## План на будущее

* Заменить правило‑ориентированную логику моделями машинного
  обучения для более точной классификации и персональных советов.
* Масштабировать AI‑сервис независимо от сервера.
* Использовать объектное хранилище (например, Amazon S3) для хранения
  выписок.
* Реализовать кэширование и ограничение частоты запросов для
  повышения производительности и защиты от злоупотреблений.
