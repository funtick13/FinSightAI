# Требования к парсеру PDF‑выписок

Этот документ описывает **требования к модулю парсинга PDF‑выписок** в рамках проекта FinSight AI. Требования сформированы на основе технического задания, архитектурного описания и схемы БД. Парсер является частью серверной части (Spring Boot) и служит для автоматического извлечения данных из загруженных PDF‑файлов.

## 1. Общие положения и границы

1. Парсер предназначен для обработки ежемесячных банковских выписок в формате PDF, загруженных пользователем через мобильное приложение. На этапе MVP поддерживаются только выписки **Сбербанка**. Поддержка других банков является задачей дальнейших фаз разработки.
2. Парсер принимает путь к PDF‑файлу и метаданные выписки (пользователь, банк, год, месяц). После обработки он возвращает список извлечённых операций, готовых для сохранения, либо сообщает об ошибке. 
3. Цель парсинга — превратить PDF‑файл в структурированный набор операций, содержащий дату, сумму, описание и категорию. Входящий PDF не должен модифицироваться; файл служит исходным источником.
4. Парсер — это **серверный процесс**. В нём не должно быть UI‑компонентов. Мобильное приложение лишь инициирует загрузку и отображает статус.
5. Парсер не занимается аналитикой или генерацией рекомендаций. Аналитические функции реализуются в AI‑сервисе. Парсер должен только передать список операций, на основе которых будет построена аналитика.

## 2. Функциональные требования

1. **Извлечение операций.**
   - Из PDF‑выписки необходимо извлечь все строки, соответствующие банковским операциям. Каждая операция включает, по крайней мере, **дату, сумму, описание и категорию**. Список операций должен быть полным: не допускается пропускать строки, если они содержат корректные данные.
   - В извлечённые данные должен входить признак типа транзакции (доход или расход). Положительные значения суммы трактуются как доходы, отрицательные — как расходы. Если в выписке знак «+» явно отсутствует, операция считается расходом. Сумма должна храниться в единицах валюты, указанной в выписке; конвертация валют в рамках MVP не выполняется.
   - **Категория** транзакции берётся напрямую из строки выписки и сохраняется без модификации. Система не проводит машинной классификации категорий на этапе MVP.
   - **Описание** операции — текстовое поле, содержащее назначение платежа или комментарий. Описание не должно быть пустым; если описание отсутствует, оно заполняется стандартным значением (например, `"Не указано"`).

2. **Нормализация данных.**
   - Парсер должен привести дату и время к стандартному формату (ISO 8601) независимо от формата в PDF. Если время отсутствует, используется `00:00:00`.
   - Сумма должна быть приведена к числовому типу (Decimal) с двумя знаками после запятой. В процессе парсинга необходимо учесть локаль (запятая как десятичный разделитель).
   - Строковые значения должны быть очищены от лишних пробелов и управляющих символов.

3. **Удаление дубликатов.**
   - При извлечении операций необходимо удалить дубликаты. Дубликат определяется как операция с совпадающими датой, временем (если есть), суммой, описанием и категорией в рамках одной выписки. Если в одном PDF встречается несколько записей, отличающихся только балансом, они считаются дубликатами и сохраняется только одна запись.
   - Возможен вариант фильтрации дублей после нормализации (на уровне сервиса), поэтому парсер может возвращать полный список, а фильтратор убирает повторы.

4. **Регистрация результата.**
   - После успешного парсинга в сущности `Statement` статус должен быть изменён с `PROCESSING` на `PROCESSED` и записано время завершения. В случае ошибки статус становится `FAILED`, а сообщение об ошибке сохраняется для отображения пользователю.
   - Парсер не должен самостоятельно сохранять операции. Возврат списка операций и обновление статуса является задачей сервиса обработки (см. раздел «Архитектура»).

5. **Обработка ошибок.**
   - Если файл PDF отсутствует, недоступен или не соответствует формату, парсер должен вернуть понятное сообщение об ошибке.
   - В случае, если в документе не найдено ни одной операции, это считается ошибкой парсинга.
   - Ошибки нормализации (например, нераспознанная дата или некорректная сумма) должны прерывать обработку соответствующей строки, но не всего файла; парсер может пропустить некорректную строку и записать предупреждение.

## 3. Архитектурные требования

Чтобы обеспечить расширяемость и чистую архитектуру, парсер разбивается на следующие компоненты:

1. **`StatementProcessingService`.** Сервис, получающий идентификатор выписки, извлекающий метаданные и путь к файлу и управляющий процессом парсинга. Он меняет статусы `UPLOADED → PROCESSING → PROCESSED/FAILED` и передаёт полученный список операций в слой сохранения данных.
2. **`PdfTextExtractor`.** Низкоуровневый компонент, который открывает PDF‑файл и возвращает его текстовое содержимое. Он не должен знать о структуре операций и не зависит от конкретного банка.
3. **`BankStatementParser` (интерфейс).** Определяет контракт метода `parse(Path filePath) : List<ParsedTransaction>`. Позволяет создавать реализацию для разных банков.
4. **`SberbankStatementParser`.** Реализация интерфейса `BankStatementParser` для выписок Сбербанка. Реализует логику разбора сырых строк в объекты `ParsedTransaction`.
5. **`TransactionNormalizer`.** Компонент, который преобразует `ParsedTransaction` в доменный объект `TransactionCandidate`: приводит типы данных, определяет тип операции, заменяет пустые значения и т. д.
6. **`DuplicateTransactionDetector`.** Слой фильтрации, который находит и удаляет дубликаты на основе правил из раздела «Функциональные требования».  

Такое разделение позволяет легко добавить поддержку других банков (через новые реализации `BankStatementParser`), настроить очереди для асинхронной обработки и тестировать каждый компонент отдельно.

## 4. Детали реализации и структуры данных

1. **Класс `ParsedTransaction`.** Временный объект, содержащий данные, извлечённые из строки PDF: 
   - `rawDate` – строка с датой (и временем, если присутствует);
   - `rawAmount` – сумма в строковом виде;
   - `rawDescription` – текстовое описание операции;
   - `rawCategory` – категория из выписки.
   
   Этот класс не должен содержать приведения типов; его задача — передать данные от парсера к нормализатору.

2. **Класс `TransactionCandidate`.** Нормализованный объект, который готов к записи в базу данных:

   | Поле            | Тип         | Описание                                      |
   |-----------------|-------------|-----------------------------------------------|
   | `date`          | `LocalDate` | Дата операции (ISO 8601)                      |
   | `time`          | `LocalTime` | Время операции, если указано                  |
   | `amount`        | `BigDecimal`| Сумма; положительная для доходов, отрицательная для расходов |
   | `type`          | Enum        | `INCOME` или `EXPENSE`                        |
   | `category`      | String      | Категория из выписки                          |
   | `description`   | String      | Описание операции                             |
   | `bank`          | String      | Имя банка (в MVP — «Сбербанк»)                |
   | `period`        | String      | Отчётный месяц в формате `YYYY‑MM`            |
   | `userId`        | UUID        | Идентификатор пользователя                    |
   | `statementId`   | UUID        | Ссылка на исходную выписку                    |

3. **Сущность `Operation`.** После сохранения `TransactionCandidate` превращается в запись таблицы **Operation**, определённой в схеме БД. В таблице операции имеют поля `date`, `amount`, `description`, `category` и внешние ключи на пользователя и выписку.

4. **Статусы выписки.** Сущность **Statement** хранит статус обработки и время обновления статуса:

   | Статус       | Описание                                                                                    |
   |--------------|---------------------------------------------------------------------------------------------|
   | `UPLOADED`   | Файл загружен пользователем, парсинг ещё не начат                                           |
   | `PROCESSING` | Выписка передана на разбор; пользователь может видеть индикатор «обработка»                 |
   | `PROCESSED`  | Парсинг завершён успешно; операции переданы в хранение                                     |
   | `FAILED`     | Произошла ошибка; детальное сообщение должно сохраняться и быть доступным для отображения   |

5. **Поток работы.** Парсер работает в рамках общего потока данных, описанного в архитектуре. После загрузки файла сервер вызывает `StatementProcessingService`, который:
   1. Меняет статус выписки на `PROCESSING`.
   2. Вызывает `PdfTextExtractor` для получения текста.
   3. Передаёт текст в `SberbankStatementParser` и получает список `ParsedTransaction`.
   4. Отдаёт список в `TransactionNormalizer`, который формирует `TransactionCandidate` и определяет тип операции по знаку суммы.
   5. Передаёт кандидаты в `DuplicateTransactionDetector` для фильтрации повторов.
   6. Возвращает итоговый список сервису, который обновляет статус выписки и инициирует сохранение операций в БД.

## 5. Ошибки и исключения

1. **Ошибка файла.** Если PDF‑файл не найден или не читается, сервис должен установить статус выписки в `FAILED` и вернуть ошибку «Файл не найден» или «Невозможно прочитать PDF».
2. **Пустой результат.** Если в документе не удалось найти ни одной операции (нет строк, удовлетворяющих шаблону), это считается ошибкой. Статус устанавливается `FAILED`.
3. **Нераспознанные данные.** Если отдельная строка не соответствует ожидаемому формату (не удалось извлечь дату или сумму), строка пропускается. Сервис должен зарегистрировать предупреждение, чтобы разработчики могли улучшить парсер.
4. **Системные ошибки.** При возникновении внутренних исключений (например, проблемы с библиотекой чтения PDF) сервис должен зафиксировать стек исключения, изменить статус выписки на `FAILED` и сообщить об ошибке пользователю.

## 6. Нефункциональные требования

1. **Производительность.** Парсер должен обрабатывать одну выписку (обычно 2–5 страниц) за приемлемое время (до нескольких секунд) без значительной задержки UI. В дальнейших версиях возможна асинхронная очередь.
2. **Расширяемость.** Архитектура должна позволять добавлять парсеры для других банков без модификации существующего кода. Для этого используется интерфейс `BankStatementParser`.
3. **Тестируемость.** Компоненты должны покрываться unit‑тестами: 
   - Тесты на `PdfTextExtractor` с примерами PDF; 
   - Тесты на `SberbankStatementParser` с реальными/смоделированными выписками; 
   - Тесты на `TransactionNormalizer` и `DuplicateTransactionDetector`.
4. **Отказоустойчивость.** При любом исключении парсинга система должна корректно сохранять статус и не приводить к потере уже загруженных файлов. Ошибки должны логироваться и не «падать» в верхний уровень.
5. **Локализация и безопасность.** Так как проект ориентирован на русскоязычных пользователей, парсер должен корректно обрабатывать русские названия категорий и описания. При хранении данных следует соблюдать требования безопасности (парсер не должен логировать персональные данные).

## 7. Ограничения и допущения

* Поддержка **одного банка** в MVP означает, что структура PDF‑файла считается фиксированной. Если в будущем структура изменится, парсер должен быть адаптирован.
* Парсер игнорирует информационные разделы (например, итоговые остатки, тарифы, рекламные вставки) и извлекает только строки с операциями.
* Парсер не проверяет подлинность документов и не проводит юридическую экспертизу. Система предназначена для исследовательских целей и не должна использоваться для официального финансового учёта.

---

**Итого:** парсер PDF‑выписок FinSight AI должен автоматически преобразовывать загруженные PDF‑файлы Сбербанка в список операций, содержащий дату, сумму, описание и категорию. Он должен фильтровать дубликаты, корректно обрабатывать ошибки и обеспечивать нормализацию данных для дальнейшего хранения. Архитектура строится по принципу разделения ответственности, что обеспечивает расширяемость и удобство поддержки в будущих версиях.
