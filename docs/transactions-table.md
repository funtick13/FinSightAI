# Хранение операций

## 1. Общие положения

Этап 6 разработки системы **FinSight AI** посвящён реализации подсистемы хранения финансовых операций, извлечённых из банковских PDF-выписок. Данный этап следует после реализации парсинга PDF-выписок Сбербанка и является связующим звеном между обработкой банковского файла, дальнейшей backend-аналитикой и последующей передачей данных в AI-сервис.

В рамках предыдущего этапа backend-парсер уже преобразует PDF-выписку в список нормализованных объектов `TransactionCandidate`. На этапе 6 эти данные должны быть преобразованы в постоянные сущности, сохранены в базе данных и предоставлены пользователю через API.

Главный результат этапа 6:

```text
PDF-выписка
→ парсинг операций
→ TransactionCandidate
→ Transaction entity
→ PostgreSQL
→ API получения операций
```

## 2. Цель этапа

Целью этапа 6 является формирование финансовой базы пользователя за счёт сохранения операций, извлечённых из банковских выписок.

После завершения этапа система должна обеспечивать:

- сохранение операций, полученных после парсинга PDF-выписки;
- привязку каждой операции к пользователю;
- привязку каждой операции к исходной банковской выписке;
- хранение банка и расчётного периода операции;
- исключение повторного сохранения дублирующихся операций;
- получение списка операций пользователя за выбранный месяц;
- получение конкретной операции по идентификатору;
- удаление операций при удалении исходной выписки.

## 3. Границы этапа

### 3.1 Входит в этап

На данном этапе необходимо реализовать:

- сущность `Transaction`;
- таблицу `transactions` в базе данных;
- репозиторий `TransactionRepository`;
- сервис `TransactionService`;
- mapper для преобразования `TransactionCandidate` в `Transaction`;
- DTO для ответа API;
- REST API для получения операций;
- интеграцию сохранения операций с `StatementProcessingService`;
- проверку дубликатов с учётом уже сохранённых операций;
- удаление операций, связанных с удаляемой выпиской;
- unit- и интеграционные тесты.


## 4. Место этапа в общей архитектуре

Подсистема хранения операций располагается внутри backend-сервера и является частью общего процесса обработки банковской выписки.

Общий поток после реализации этапа 6:

```text
Flutter mobile app
    ↓
Backend: загрузка PDF-выписки
    ↓
Statement сохраняется в БД
    ↓
StatementProcessingService запускает обработку
    ↓
PdfTextExtractor извлекает текст
    ↓
SberbankStatementParser извлекает операции
    ↓
TransactionNormalizer формирует TransactionCandidate
    ↓
DuplicateTransactionDetector удаляет дубли внутри списка
    ↓
TransactionService сохраняет операции в БД
    ↓
Statement получает статус PROCESSED
    ↓
GET /api/operations возвращает операции пользователю
```

Сервис хранения операций не должен заниматься парсингом PDF и не должен выполнять аналитику. Его ответственность — принять уже подготовленные финансовые операции и корректно сохранить их в базе данных.

## 5. Основная сущность этапа — Transaction

### 5.1 Назначение сущности

Сущность `Transaction` предназначена для хранения отдельной финансовой операции пользователя, извлечённой из банковской выписки.

Операция является основой для последующих функций системы:

- расчёта доходов и расходов;
- группировки расходов по категориям;
- построения графиков;
- формирования финансовой аналитики;
- передачи данных в AI-сервис;
- генерации рекомендаций.

### 5.2 Поля сущности

Сущность `Transaction` должна содержать следующие поля:

| Поле | Тип | Назначение |
|------|-----|------------|
| `id` | UUID | Уникальный идентификатор операции |
| `user` | User | Пользователь, которому принадлежит операция |
| `statement` | Statement | Выписка, из которой была извлечена операция |
| `bank` | BankType | Банк, к которому относится операция |
| `period` | String | Расчётный период в формате `YYYY-MM` |
| `date` | LocalDate | Дата совершения операции |
| `time` | LocalTime | Время операции; если отсутствует — `00:00` |
| `type` | TransactionType | Тип операции: `INCOME` или `EXPENSE` |
| `amount` | BigDecimal | Сумма операции |
| `category` | String | Категория операции из банковской выписки |
| `description` | String | Текстовое описание операции |
| `createdAt` | LocalDateTime | Дата и время сохранения операции в системе |

### 5.3 Требования к полям

Поле `user` является обязательным. Операция не может существовать без связи с пользователем.

Поле `statement` является обязательным. Каждая операция должна быть связана с выпиской, из которой она была получена.

Поле `bank` должно соответствовать банку исходной выписки. В рамках MVP используется значение `SBERBANK`.

Поле `period` должно совпадать с расчётным периодом исходной выписки.

Поле `amount` должно храниться в числовом формате `BigDecimal`. Для расходов допускается хранить отрицательное значение, если такой подход уже используется в нормализаторе. При этом тип операции также должен быть явно сохранён в поле `type`.

Поле `category` должно содержать категорию, извлечённую из выписки. Если категория отсутствует, должно использоваться значение `Прочее`.

Поле `description` должно содержать очищенное текстовое описание операции без служебных хвостов, номеров карт и другой лишней информации, если такая очистка уже выполняется парсером.

## 6. Проектирование таблицы базы данных

Для хранения операций необходимо создать таблицу `transactions`.

Пример структуры таблицы:

```sql
create table transactions (
    id uuid primary key,

    user_id uuid not null,
    statement_id uuid not null,

    bank varchar(50) not null,
    period varchar(7) not null,

    operation_date date not null,
    operation_time time not null,

    type varchar(20) not null,
    amount numeric(19, 2) not null,

    category varchar(255) not null,
    description text not null,

    created_at timestamp not null,

    constraint fk_transactions_user
        foreign key (user_id) references users(id),

    constraint fk_transactions_statement
        foreign key (statement_id) references statements(id)
);
```

### 6. Уникальность и дубликаты

Дубликат операции в рамках MVP определяется по комбинации:

```text
user_id + bank + period + operation_date + operation_time + amount + description
```

На первом шаге проверку дублей можно выполнять на уровне сервиса. После стабилизации модели данных допускается добавить уникальный индекс, если это не приведёт к ошибкам при обработке неоднозначных банковских строк.

## 7. TransactionType

На этапе парсинга уже используется enum `TransactionType`.

Он должен содержать значения:

```java
public enum TransactionType {
    INCOME,
    EXPENSE
}
```

Назначение:

- `INCOME` — доходная операция;
- `EXPENSE` — расходная операция.

Тип операции должен определяться на этапе нормализации на основе знака суммы из банковской выписки.

## 8. TransactionRepository

### 8.1 Назначение репозитория

`TransactionRepository` предназначен для доступа к данным операций в базе данных.

Репозиторий должен обеспечивать:

- сохранение операций;
- получение операций пользователя за период;
- получение операции по идентификатору и пользователю;
- получение операций по выписке;
- проверку существования операции-дубликата;
- удаление операций, связанных с выпиской.

### 8.2 Основные методы

Рекомендуемый набор методов:

```java
public interface TransactionRepository extends JpaRepository<Transaction, UUID> {

    List<Transaction> findAllByUserIdAndPeriodOrderByDateDescTimeDesc(
        UUID userId,
        String period
    );

    Optional<Transaction> findByIdAndUserId(
        UUID id,
        UUID userId
    );

    List<Transaction> findAllByStatementId(
        UUID statementId
    );

    void deleteAllByStatementId(
        UUID statementId
    );

    boolean existsByUserIdAndBankAndPeriodAndDateAndTimeAndAmountAndDescription(
        UUID userId,
        BankType bank,
        String period,
        LocalDate date,
        LocalTime time,
        BigDecimal amount,
        String description
    );
}
```

Названия методов необходимо адаптировать под фактические имена полей в сущности `Transaction`.

## 9. TransactionService

### 9.1 Назначение сервиса

`TransactionService` реализует бизнес-логику хранения и получения финансовых операций.

Сервис должен быть единственной точкой, через которую другие компоненты backend-системы сохраняют или получают операции.

### 9.2 Основные методы

```java
List<Transaction> saveCandidates(List<TransactionCandidate> candidates);

List<TransactionResponse> getUserTransactions(UUID userId, String period);

TransactionResponse getUserTransaction(UUID userId, UUID transactionId);

void deleteByStatementId(UUID statementId);
```

### 9.3 Логика метода saveCandidates

Метод `saveCandidates` должен выполнять следующие действия:

1. Принять список `TransactionCandidate`.
2. Проверить, что список не равен `null` и не является пустым.
3. Для каждого кандидата проверить наличие дубля в базе данных.
4. Если дубль найден, не сохранять операцию повторно.
5. Если дубль не найден, преобразовать кандидата в сущность `Transaction`.
6. Сохранить операции через `saveAll`.
7. Вернуть список сохранённых операций.

Если все операции оказались дублями, это не должно считаться критической ошибкой. В этом случае сервис может вернуть пустой список сохранённых операций, но обработка выписки должна завершиться корректно, если сам парсинг был успешным.

## 10. TransactionMapper

### 10.1 Назначение mapper

`TransactionMapper` отвечает за преобразование объектов между слоями приложения.

Он должен выполнять:

- преобразование `TransactionCandidate` в `Transaction`;
- преобразование `Transaction` в `TransactionResponse`.

### 10.2 Методы

```java
Transaction toEntity(TransactionCandidate candidate, User user, Statement statement);

TransactionResponse toResponse(Transaction transaction);
```

Если `TransactionCandidate` уже содержит `userId` и `statementId`, mapper должен использовать их для установки связей через найденные сущности `User` и `Statement`.

Mapper не должен выполнять проверку дублей, работу с базой данных или изменение статусов выписки.

## 11. TransactionResponse

### 11.1 Назначение DTO

`TransactionResponse` предназначен для возврата операции во внешнем API backend-сервера.

### 11.2 Структура ответа

|---------|-----|----------------|----------|
| `period` | String | Да | Расчётный месяц в формате `YYYY-MM` |

Ответ:

```json
[
```

### 12.2 Получение одной операции

Endpoint:


Требование безопасности:

- пользователь может получить только свою операцию;
- если операция принадлежит другому пользователю, система не должна раскрывать её данные.

## 13. Интеграция с StatementProcessingService

После реализации хранения операций необходимо доработать `StatementProcessingServiceImpl`.

Текущий поток:

```text
StatementProcessingService
→ parser
→ normalizer
→ duplicate detector
→ List<TransactionCandidate>
→ Statement PROCESSED
```

Целевой поток этапа 6:

```text
StatementProcessingService
→ parser
→ normalizer
→ duplicate detector
→ TransactionService.saveCandidates(...)
→ Statement PROCESSED
```

Статус `PROCESSED` должен выставляться только после успешного завершения сохранения операций.

Если парсинг успешен, но сохранение операций завершилось ошибкой, выписка должна получить статус `FAILED`, а поле `errorMessage` должно содержать понятное описание ошибки.

Метод `processStatementToCandidates(UUID statementId)` можно оставить для тестирования и отладки, но основной production-поток должен сохранять операции в БД.

## 14. Интеграция с удалением выписки

При удалении банковской выписки необходимо удалить операции, связанные с этой выпиской.

Целевой порядок удаления:

```text
1. Найти Statement по id и текущему пользователю.
2. Удалить все Transaction, связанные с Statement.
3. Удалить PDF-файл из файлового хранилища.
4. Удалить запись Statement из БД.
5. Позже — инициировать пересчёт аналитики.
```

На этапе 6 пересчёт аналитики ещё не реализуется, но место для будущего вызова нужно учитывать.

## 15. Валидация

### 15.1 Валидация периода

Для API получения операций параметр `period` обязателен.

Формат периода:

```text
YYYY-MM
```

Примеры корректных значений:

```text
2026-04
2026-12
```

Примеры некорректных значений:

```text
2026
04-2026
2026/04
2026-13
```

При некорректном периоде backend должен вернуть ошибку `400 Bad Request`.

### 15.2 Валидация доступа

Все endpoints операций должны быть защищены JWT.

Пользователь не должен иметь возможности:

- получить чужие операции;
- получить операцию по id, если она принадлежит другому пользователю;
- удалить операции напрямую без удаления связанной выписки.

## 16. Обработка ошибок

Необходимо обработать следующие ситуации:

| Ситуация | Поведение системы |
|---------|-------------------|
| Период не передан | Вернуть `400 Bad Request` |
| Период имеет неверный формат | Вернуть `400 Bad Request` |
| Операция не найдена | Вернуть `404 Not Found` |
| Операция принадлежит другому пользователю | Вернуть `404 Not Found` или `403 Forbidden` согласно текущей политике проекта |
| Ошибка сохранения операций | Установить `Statement` в `FAILED` |
| Список кандидатов пустой | Не сохранять операции, обработать как допустимую ситуацию только если парсинг не является ошибочным |
| Ошибка связи с Statement | Вернуть доменную ошибку обработки |
| Дубликат операции | Не сохранять повторно |

Тексты ошибок должны быть понятными для пользователя и не должны содержать stacktrace.

## 17. Требования безопасности

При реализации этапа 6 необходимо соблюдать следующие требования:

- все API операций должны быть доступны только авторизованным пользователям;
- операции должны фильтроваться по текущему пользователю;
- нельзя возвращать операции другого пользователя;
- нельзя логировать персональные данные, номера карт, номера счетов и полный текст выписки;
- нельзя сохранять PDF-файлы или реальные выписки в git;
- нельзя отправлять PDF-файл в AI-сервис;
- нельзя реализовывать ручное изменение операций, если это не предусмотрено MVP.

### 19.1 Unit-тесты

- `StatementProcessingServiceImplTest` с проверкой сохранения операций;

### 19.2 Проверяемые сценарии

Тестами необходимо покрыть:

- успешное сохранение списка операций;
- сохранение пустого списка;
- фильтрацию дублей;

### 19.3 Ручная проверка через API

После загрузки PDF-выписки проверить таблицу `transactions`:

```sql
select count(*)
from transactions
where statement_id = '<statement-id>';
```

Если тестовая выписка содержит 72 операции, после обработки должно быть сохранено 72 операции, если среди них нет дублей.

Проверить статус выписки:

```sql
select status, processed_at, error_message
from statements
where id = '<statement-id>';
```

Ожидаемый результат:

```text
status = PROCESSED
processed_at is not null
error_message is null
```

Проверить API:

```http
GET /api/operations?period=2026-04
```

Ожидаемый результат:

```text
HTTP 200 OK
список операций текущего пользователя
```

## 20. Критерии готовности этапа

Этап 6 считается завершённым, если выполнены следующие условия:

- создана таблица `transactions`;
- создана сущность `Transaction`;
- операции сохраняются после парсинга PDF;
- каждая операция связана с пользователем и выпиской;
- у каждой операции сохранены банк и расчётный период;
- реализована проверка дублей с учётом БД;
- реализован API получения операций;
- пользователь может получить только свои операции;
- при удалении выписки удаляются связанные операции;
- `Statement` получает статус `PROCESSED` только после успешного сохранения операций;
- при ошибке сохранения `Statement` получает статус `FAILED`;
- тесты проходят;
- существующая загрузка PDF и парсер не сломаны.

## 21. Итоговая схема после этапа 6

После завершения этапа 6 backend-система должна иметь следующий рабочий поток:

```text
Пользователь загружает PDF
    ↓
Backend сохраняет Statement
    ↓
StatementProcessingService запускает обработку
    ↓
Парсер извлекает операции
    ↓
TransactionNormalizer формирует TransactionCandidate
    ↓
DuplicateTransactionDetector удаляет дубли
    ↓
TransactionService сохраняет Transaction в БД
    ↓
Statement получает PROCESSED
    ↓
Пользователь получает операции через GET /api/operations
```

## 22. Переход к следующему этапу

После завершения этапа 6 можно переходить к этапу 7 — базовой backend-аналитике.

Этап 7 будет использовать сохранённые операции для расчёта:

- общей суммы доходов;
- общей суммы расходов;
- баланса за период;
- расходов по категориям;
- данных для графиков;
- подготовленных данных для AI-сервиса.

Таким образом, этап 6 формирует основу для всей последующей финансовой аналитики системы.
